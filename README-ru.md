# Scholion

> **Языково-независимый препроцессор с Lua-макросами.**

[![Go](https://img.shields.io/badge/Go-1.26+-00ADD8?logo=go)](https://go.dev)
[![License](https://img.shields.io/badge/License-Apache%202.0-blue.svg)](LICENSE)
[![Made with lc](https://img.shields.io/badge/engine-pt--main%2Flc-purple)](https://github.com/pt-main/lc)

Scholion превращает ваш исходный файл в программу генерации самого себя. Директивы в комментариях выполняются встроенным Lua-интерпретатором, который умеет генерировать код, управлять буферами, регистрировать собственные DSL и делиться данными между изолированными состояниями. На выходе - готовый к компиляции файл.

## Проблема

### 1. Генерация кода живёт отдельно от кода

Сегодня метапрограммирование почти всегда вынесено за пределы исходника:

- `protoc`, `mockgen`, `stringer`, `sqlc`, `go generate` - отдельные утилиты;
- `text/template`, `Jinja`, `mustache` - отдельные файлы шаблонов;
- `m4`, `Cog`, `scons`-стайл - отдельные проходы сборки.

Проблема одна и та же: **сгенерированное отделено от того, что его породило**. Правки в шаблон не видны в месте использования, контекст теряется, навигация ломается, а диагностика ошибок указывает на "чужой" файл. В итоге приходится держать в голове два мира и синхронизировать их вручную.

### 2. Во многих языках нет макросов

- **Go** не имеет макросов (generics не заменяют их для кодогенерации).
- **C/C++** имеет только текстовый препроцессор, который не умеет ни в типы, ни в циклы, ни в рефлексию.
- **Java, C#, Python, TypeScript** - либо reflection, либо кодогенерация, либо ничего.

Разработчик остаётся с дилеммой: либо писать однообразный код руками, либо строить внешний генератор.

### 3. Существующие инструменты заточены под один язык

`go generate` работает только с Go. `cargo-expand` - только с Rust. `cpp` - только с C/C++. Если у вас монорепозиторий на пяти языках или собственный DSL, вам нужен **один** инструмент, а не пять.

### 4. Специализированные препроцессоры слишком слабы

`m4` мощен, но его синтаксис - это боль. `Cog` умеет Python, но привязан к Python. `scons` - это сборщик, а не препроцессор. Ни один из них не даёт одновременно:

- встраивания прямо в исходник,
- полноценного скриптового языка,
- регистрации собственных паттернов,
- независимости от целевого языка.

**Итог:** нужен инструмент, который работает *внутри* файла, на *любом* языке, даёт *полноценный* скриптовый язык и позволяет *расширять себя* под задачу.

## Решение

### Три опоры Scholion

1. **Комментарии как носители директив.** Файл остаётся валидным для целевого языка - IDE, линтеры, компилятор ничего не замечают.
2. **Lua как язык макросов.** Маленький (≈450 КБ), быстрый, встраиваемый (`gopher-lua`, чистый Go), знакомый миллионам разработчиков.
3. **Пользовательские DSL через `sys.register`.** Вы определяете собственные паттерны и получаете мини-язык прямо в комментариях.

### Как это выглядит

До обработки - `server.go.schol`:

```go
package main

import "fmt"

//# lua eval print("starting...")
//# lua eval sys.emitln("\nimport \"net/http\"")

//# lua eval for i=1, 3 do sys.emit(string.format("\nvar Port%d int = %d", i, 8000+i)) end

// DSL: ROUTE: <method> <path> => <handler>
/*# lua eval
sys.register([[^\s*ROUTE:\s*(?<method>\w+)\s+(?<path>\S+)\s*=>\s*(?<handler>\w+)]], function(args)
    sys.emitln(string.format("func %s(w http.ResponseWriter, r *http.Request) {", args.handler))
    sys.emitln("    w.WriteHeader(http.StatusOK)")
    sys.emitln("}")
end)
*/

//# ROUTE: GET /users => HandleGetUsers
//# ROUTE: POST /users => HandleCreateUser

func main() {
	fmt.Println("Server starting...")
}
```

После `schol server.go.schol` - `server.go.schol_compiled.go`:

```go
package main

import "fmt"
import "net/http"

var Port1 int = 8001
var Port2 int = 8002
var Port3 int = 8003

func HandleGetUsers(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
}
func HandleCreateUser(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
}

func main() {
	fmt.Println("Server starting...")
}
```

**Файл остаётся компилируемым на всех этапах.** Директивы - это просто комментарии для компилятора и макросы для Scholion.

## Почему именно так

### Почему комментарии, а не специальный синтаксис?

| Подход | Плюсы | Минусы |
|---|---|---|
| **Спецсинтаксис** (`#macro`, `@gen`) | Явно, подсвечивается | Ломает парсер целевого языка, требует форка |
| **Отдельные файлы** (`*.gen.go`) | Чисто | Теряется контекст, две правды |
| **Комментарии** (наш выбор) | Файл валиден, работает везде, IDE-дружелюбно | Визуальный шум при злоупотреблении |

Комментарии - единственное место в языке, где **гарантированно** можно писать что угодно, не нарушая грамматику. Scholion использует это как точку входа. Если вы переусердствовали с директивами - это вопрос стиля, а не архитектуры.

### Почему Lua, а не Python / JS / свой язык?

- **`gopher-lua`** - чистый Go, без cgo, ~450 КБ бинарника, встраивается в одну строку.
- **Скорость старта** - доли миллисекунды против сотен у CPython.
- **Простой C-API** - легко контролировать песочницу и стек.
- **Знакомый синтаксис** - таблицы, замыкания, метатаблицы, `string.format`, `gmatch` - всё уже есть.
- **Альтернативы хуже**: Python тянет cgo и десятки мегабайт; JS-движки огромны; собственный язык - это годы работы.

Lua - это "достаточно мощно и достаточно дёшево". Если вам нужен именно DSL, вы всё равно строите его поверх Lua (`sys.register` + замыкания), а не пишете парсер с нуля.

### Почему `regexp2`, а не стандартный `regexp`?

Стандартный `regexp` в Go - это RE2: линейное время, но **нет**:

- lookahead/lookbehind,
- обратных ссылок,
- именованных групп в .NET-синтаксисе `(?<name>...)`,
- ленивых квантификаторов в полном объёме.

Scholion использует `github.com/dlclark/regexp2` - порт .NET Regex. Это даёт:

- **именованные группы** `(?<value>...)` - на них построен весь API (`m["value"]`);
- **ленивые квантификаторы** `.*?` для аккуратного захвата блоков;
- **флаги** `(?s)`, `(?m)` в одном месте;
- **backtracking** - предсказуемое поведение для типичных паттернов DSL.

Цена - потенциальная катастрофическая backtracking-уязвимость на враждебных паттернах. В Scholion паттерны пишет сам пользователь, так что это осознанный компромисс: гибкость важнее паранойи.

### Почему Tessera, а не YAML/JSON/TOML?

Tessera - конфигурационный формат, заточенный под:

- **плоские строки** (`comment s //`) без кавычек;
- **вложенные таблицы** (`<flags ... >`) - именно то, что нужно для передачи флагов в Lua;
- **типизацию** (`s`, `i`, `f`, `l`), если она нужна.

YAML был бы избыточен и опасен (the Norway problem), JSON - слишком много кавычек для конфига из пяти строк, TOML - тоже оверкилл. Tessera - это "JSON для людей, которым лень писать кавычки". Один и тот же формат использует и `run`, и другие проекты автора - экосистема.

### Почему буферы, состояния и общий `scope`?

Это три разных механизма для трёх разных задач:

- **Буферы** - накопить фрагмент вывода, а потом вставить его целиком (`paste`). Полезно, когда код генерируется нелинейно: сначала собери "шапку", потом "тело", потом склей.
- **Состояния** - изоляция. Включённый файл не должен случайно перезаписать глобальные переменные основного скрипта. `lua new tmp` создаёт отдельный Lua-мир.
- **Общий `scope`** - единственная таблица, разделяемая всеми состояниями. Через неё передаются данные между изолированными мирами.

Без разделения получилось бы либо "всё в одном глобальном пространстве" (конфликты), либо "всё изолировано" (невозможно общаться). Три уровня - минимум для реальных сценариев.

### Почему first-match-wins в диспетчеризации?

В `Dispatch.patterns` паттерны перебираются **в порядке регистрации**, побеждает первый совпавший. Это:

- **предсказуемо** - вы контролируете порядок вызовом `AddPattern`;
- **расширяемо** - пользователь может зарегистрировать более специфичный паттерн *раньше* встроенного;
- **отлаживаемо** - если паттерн "съел" чужую директиву, достаточно переставить регистрацию.

### Почему лексер, а не построчный `strings.HasPrefix`?

Строки, блочные комментарии и многострочные директивы - это три вещи, которые ломают наивный построчный парсер:

- `x := "//# not a directive"` - строка, не директива;
- `/*# ... \n ... \n */` - блок, а не строка;
- `` `` `` `` `` `` ``...` `` `` `` - бэктики с переносами.

Лексер сначала выдёргивает **строковые литералы** отдельными правилами, а уже потом ищет директивы. Это единственный способ не путать данные с управляющими конструкциями.

## Быстрый старт

### 1. Создайте файл

`hello.go.schol`:

```go
package main

import "fmt"

//# lua eval print("generating...")
//# lua eval for i=1, 3 do sys.emitln(string.format("var N%d = %d", i, i)) end

func main() {
	fmt.Println("hello")
}
```

### 2. Запустите

```bash
schol hello.go.schol
```

### 3. Смотрите результат

`hello.go.schol_compiled.go`:

```go
package main

import "fmt"

var N1 = 1
var N2 = 2
var N3 = 3

func main() {
	fmt.Println("hello")
}
```

По умолчанию выходной файл - `<input>_compiled.<ext>`. Явно:

```bash
schol hello.go.schol hello.go
```

## Директивы

### Синтаксис

Директива - это комментарий, начинающийся с `#` сразу после маркера комментария. Ведущие пробелы сохраняются (отступ не теряется).

**Строчная** (для `//`):

```
<comment>#<директива>
```

**Блочная** (для `/* ... */`):

```
<blockStart>#<директива><blockEnd>
```

Блочная форма поддерживает многострочность:

```
/*# lua eval
sys.emitln("line 1")
sys.emitln("line 2")
*/
```

Синтаксис комментариев настраивается через CLI (`--comment`, `--commentBlockStart`, `--commentBlockEnd`) или через конфиг (см. ниже). По умолчанию - C/Go/PHP-стиль: `//`, `/*`, `*/`.

### Что НЕ является директивой

- Строки: `x := "//# not a directive"` - `//#` внутри строкового литерала не парсится.
- Комментарии не в начале строки: `foo //# not a directive` - директива должна быть в начале строки (допускаются ведущие пробелы).
- Неизвестные директивы: `//# unknown foo` → ошибка `No matched patterns` (см. [Ошибки](#ошибки-и-отладка)).

### Экранирование

Внутри значения директивы поддерживаются экранирования, чтобы генерировать символы, конфликтующие с синтаксисом комментариев:

| Последовательность | Результат |
|---|---|
| `\\` | `\` |
| `\C` | Префикс строчного комментария (`//`) |
| `\E` | Конец блочного комментария (`*/`) |

Пример:

```
/*# lua eval sys.emit("before\n\E\nafter") */
```

Выведет `before\n*/\nafter` - то есть literal `*/` в сгенерированном коде, не закрывая текущий блок.

### Lua-команды

Внутри директив `lua` доступны команды:

| Команда | Описание |
|---|---|
| `lua eval <code>` | Выполнить код в состоянии по умолчанию (`main`). |
| `lua eval:<state> <code>` | Выполнить код в указанном состоянии. |
| `lua exec:<buffer>` | Выполнить код из буфера в `main`. |
| `lua exec:<buffer>:<state>` | Выполнить код из буфера в указанном состоянии. |
| `lua new <state>` | Создать новое изолированное Lua-состояние. |
| `lua close <state>` | Закрыть состояние. |

Разбор команды: первое слово после `lua` (до пробела/переноса) - это команда, всё остальное - аргумент. Поэтому `lua eval print("x")` и `lua eval\nprint("x")` эквивалентны.

### Другие директивы

Помимо `lua`, Scholion регистрирует четыре директивы:

| Директива | Описание |
|---|---|
| `include <file> [state]` | Прочитать файл и выполнить его как Lua-код в состоянии `state` (по умолчанию `main`). Если состояния нет - оно будет создано. |
| `append <file>` | Прочитать файл и вставить его содержимое напрямую в выходной буфер без выполнения через Lua (поддерживает список файлов построчно в блочной директиве). |
| `end` | Закрыть **все** Lua-состояния и завершить обработку. |
| `echo <text>` | Вывести текст в stdout без перевода строки (`\n` в тексте → перенос). |
| `echoln <text>` | Вывести текст в stdout с переводом строки. |

## Lua API

В каждом состоянии доступны глобальные таблицы `sys`, `state`, `buffers`, `flags` и общая `scope`.

### Безопасность и песочница
По умолчанию стандартные библиотеки Lua отключены в целях безопасности. Макросы не могут выполнять системные команды или читать произвольные файлы с диска. 

Чтобы получить доступ к stdlib Lua, используйте специальный флаг `__state_flags` типа `s`. Внутри него находятся флаги, разделенные пробелами. Он обозначает как создавать Lua состояние. Доступные флаги:

- `open-libs` - включает стандартную библиотеку.
- `safe-mode:io` - ограничить io open, popen.
- `safe-mode:os` - ограничить os execute, remove, rename, exit, setlocale.
- `safe-mode` - включить все вышеописанные ограничения.
- `verbose` - добавляет отладочные данные в вывод.

Например, чтобы включить Lua stdlib с ограничениями безопасности:

```text
<flags
  __state_flags s "open-libs safe-mode"
>
```

### `sys` - вывод и регистрация

```lua
sys.emit("a", "b", "c")          -- записать строки в основной буфер кода
sys.emitln("a", "b", "c")        -- то же + "\n"
sys.skip(2)                      -- пропустить следующие 2 RAW-токена
sys.schol("lua eval print('x')") -- выполнить schol-директиву рекурсивно
sys.register(pattern, fn)        -- зарегистрировать DSL-паттерн
```

`sys.skip(n)` полезен, когда вы генерируете код вместо исходных строк: следующие `n` строк из файла не попадут в вывод.

`sys.schol(code)` - рекурсивный вызов: переданная строка проходит ту же диспетчеризацию, что и обычная директива. Удобно, если вы строите директиву динамически.

`sys.register(regex, fn)` - см. отдельный [раздел](#собственный-dsl-через-sysregister).

### `state` - изолированные состояния

```lua
state.new("tmp")                       -- создать состояние
state.execute("tmp", "return 1 + 1")   -- выполнить и получить результат
state.close("tmp")                     -- закрыть
```

`state.execute(state, code)` оборачивает код в функцию, вызывает её и возвращает последний `return`:

```lua
local r = state.execute("tmp", "local x = 8; return x + 2")
print(r) -- 10
```

Это единственный способ получить значение из другого состояния в текущее.

### `buffers` - накопители

Буферы живут на уровне процессора (`Processor.Sys.Buffers`) и **разделяются** между всеми состояниями.

```lua
local name = buffers.new()           -- "__tmp_buf_n0"
buffers.append(name, "a")            -- -> ["a"]
buffers.prepend(name, "z")           -- -> ["z", "a"]
local s = buffers.get(name)          -- "za"
buffers.paste(name)                  -- записать "za" в основной код
buffers.clear(name)                  -- очистить
buffers.delete(name)                 -- удалить
```

Типичный сценарий: собрать несколько фрагментов в буфер, потом вставить одним куском - чтобы не заботиться о порядке вывода.

### `flags` - флаги из конфига

```lua
flags.debug                 -- прямой доступ
flags:get("debug")          -- через метод
flags:set("debug", "true")
flags:has("debug")
flags:delete("debug")
flags:clear()
flags:list()                -- копия таблицы
```

Флаги инициализируются из секции `<flags>` в Tessera-конфиге и **не** мутируют `Processor` - таблица живёт в конкретном состоянии. Изменения в одном состоянии не видны в другом (кроме тех, что были в конфиге изначально). Это намеренное ограничение; для обмена используйте `scope`. 

### `scope` - общая таблица

Одна Lua-таблица на весь процессор, разделяемая всеми состояниями:

```lua
-- в main
scope.counter = 0

-- в tmp
scope.counter = scope.counter + 1
print(scope.counter) -- 1
```

Это рекомендуемый способ обмена данными между изолированными состояниями.

### `source` - текущий код и позиция

Глобальная `source` даёт доступ к тому, что уже накоплено в основном буфере `Processor.Code`, а также к текущей позиции в исходнике. Все значения читаются динамически на момент вызова.

```lua
local c = source()            -- текущий код как строка
local c = source.code()       -- то же самое, явный алиас
local ln = source.line()      -- текущая строка (1-based)
local tk = source.token()     -- текущий токен (1-based)

print(#source)                -- длина кода в байтах
print(tostring(source))       -- то же, что source()
print("--- begin ---\n" .. source .. "\n--- end ---")
```

Методы - обычные функции, поэтому вызываются и через `:`, и через `.`:

```lua
print(source:line())          -- эквивалентно source.line()
```

## Собственный DSL через `sys.register`

`sys.register(pattern, fn)` добавляет паттерн в диспетчер. Когда строка директивы совпадает с `pattern`, вызывается `fn` с таблицей именованных групп.

```lua
-- Регистрируем "enum Name V1 V2 V3"
sys.register([[^\s*enum\s+(?<name>\w+)\s+(?<values>.+)$]], function(args)
    sys.emitln("type " .. args.name .. " int")
    sys.emitln("const (")
    local i = 0
    for v in args.values:gmatch("%S+") do
        sys.emitln(string.format("    %s%s %s = %d",
            args.name, v, args.name, i))
        i = i + 1
    end
    sys.emitln(")")
end)
```

Использование:

```
//# enum Color Red Green Blue
```

Правила:

- Паттерн должен начинаться с `^\s*` - директива приходит уже с обрезанным `#` и пробелом, но с ведущими пробелами строки.
- Именованные группы `(?<name>...)` попадают в `args.name`.
- Первый совпавший паттерн побеждает. Порядок регистрации = порядок приоритета.
- Если паттерн не компилируется, `sys.register` поднимает Lua-ошибку.

Библиотека готовых DSL (`arr`, `range`, `split`, `enum`, `enumm`, `emitif`, `tpl`) лежит в [`libs/tessera.lua`](libs/tessera.lua). Её можно подключать через `include`:

```
//# include libs/tessera.lua main
```

## Внутреннее устройство

### Конвейер

```
          ┌──────────┐    ┌───────────┐    ┌─────────────┐    ┌──────────┐
source -> │  Lexer   │ -> │ Processor │ -> │ Dispatching │ -> │ Lua API  │ -> output
          │ (lc)     │    │ (RAW/DIR) │    │ (regexp2)   │    │ (gopher) │
          └──────────┘    └───────────┘    └─────────────┘    └──────────┘
```

1. **Lexer** (`lcproc.Syntax.Lexer`) режет входной поток на `RAW` и `DIRECTIVE` токены. Строковые литералы и блочные комментарии распознаются отдельными правилами - поэтому `"//# not a directive"` не станет директивой.
2. **Processor** (`processing.Processor`) обрабатывает токены:
   - `RAW` → `RawHandler` → в `Code` (или пропускается при `sys.skip`);
   - `DIRECTIVE` → `DirectiveHandler` → `Execute`.
3. **Dispatching** перебирает зарегистрированные `regexp2`-паттерны и вызывает первый совпавший.
4. **Lua API** (`luaApi.LuaApi`) предоставляет `sys`, `state`, `buffers`, `flags`, `scope` и выполняет Lua-код через `gopher-lua`.

### Processor

- `Code []string` - итоговый вывод (склеивается через `strings.Join`).
- `Sys.Buffers map[string][]string` - именованные буферы.
- `Sys.skipRawTokens uint` - счётчик пропускаемых RAW-токенов.
- `Disp` - диспетчер паттернов.

`GetCode()` возвращает `strings.Join(p.Code, "")`.

### Dispatching

```go
type Dispatch struct {
    patterns    []*regexp2.Regexp
    sources     []string
    Functions   []DirectiveFunc
    nameCounter int
}
```

`AddPattern(source, handler)` компилирует `regexp2` и добавляет в конец. `Execute(s)`:

1. Перебирает `patterns` по порядку.
2. Для первого совпадения - собирает именованные группы в `map[string]string`.
3. Вызывает `Functions[idx](p, groups)`.
4. Если ничего не совпало - `MatchError`.

### Lua API

- `LuaApi.States map[string]*lua.LState` - все состояния.
- `LuaApi.p *processing.Processor` - ссылка на процессор (для `sys.emit` и `buffers`).
- `LuaApi.Shared *lua.LTable` - таблица `scope`, общая для всех состояний.
- `LuaApi.Flags map[string]string` - исходные флаги (используются при создании новых состояний).

Каждый `NewLState` создаёт `gopher-lua`-состояние и регистрирует в нём таблицы `sys`, `state`, `buffers`, `flags`, `scope`.

## Ошибки и отладка

Коды ошибок определены в [`lang/lcproc/errors.go`](lang/lcproc/errors.go):

| Код | Когда возникает |
|---|---|
| `WrappedScholionError` | Обёртка любой ошибки внутри обработчика. |
| `ScholionMatchError` | Ни один паттерн не совпал (`No matched patterns`). |
| `ScholionInvalidPatternError` | `regexp2.Compile` не смог скомпилировать паттерн. |
| `ScholionFromLuaDirectiveError` | Ошибка разбора `lua`-команды (`eval`, `exec`, `new`, `close`). |
| `ScholionFromLuaError` | Ошибка выполнения Lua-кода. |
| `ScholionFromIncludeDirectiveError` | Ошибка `include` (файл не найден, ошибка в Lua). |
| `ScholionDirectiveFunctionError` | Ошибка внутри пользовательского обработчика. |

### Типичные проблемы

- **`No matched patterns`** - директива не распознана. Проверьте, что паттерн зарегистрирован (через `lua eval` или `include`), и что порядок регистрации не "съел" директиву более широким паттерном.
- **Директива внутри строки сработала** - значит, строка попала в лексер как RAW, но вы ожидали иначе. Проверьте кавычки (`"..."`, `'...'`, `` `...` ``).
- **`\E` не сработал** - экранирование работает только в *значении* директивы, не в теле Lua-кода. В Lua используйте `"\\E"`.
- **Флаги не видны в другом состоянии** - это ожидаемо: `flags` мутируется локально. Используйте `scope`.

### Отладочные точки

В `lang/main.go` закомментированы строки для включения подробного лога `lc`:

```go
// l := e.UEP.Logger.(*core.Logger)
// l.Logging[public.LogEvents] = true
// l.Logging[public.LogParsing] = true
// l.Logging[public.LogVerbose] = true
```

Раскомментируйте - получите поток событий парсинга в stdout.

## Ограничения и компромиссы

Осознанные ограничения текущей версии:

1. **Нет AST-анализа.** Scholion работает с текстом и комментариями, не понимает семантику целевого языка. Следствие: работает на любом языке, но не может, например, "переименовать все вызовы функции".
2. **Порядок директив критичен.** Первый совпавший паттерн побеждает; широкие паттерны могут заглушить узкие.
3. **`flags` не разделяются между состояниями.** Только `scope` разделяется.
4. **`end` закрывает все состояния сразу.** Нет способа закрыть "все, кроме одного".
5. **`sys.register` привязан к состоянию-регистратору.** Если состояние закрыть, его зарегистрированные паттерны останутся в диспетчере, но колбэк упадёт при вызове.
6. **Паттерны - это regex, не парсер.** Для сложных DSL с вложенностью лучше строить парсер в Lua.
